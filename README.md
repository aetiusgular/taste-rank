# taste-rank

Personalized fashion retrieval and ranking: a LoRA fine-tune measured on held-out customers.

Built in phases with the forge method. Phase P1: research and the pick are in `research/P1.md`, the build is in `SPEC.md`. Phase P2: the frozen split rule, metrics and seams are in `contracts/`, synthetic fixtures in `fixtures/`, and the red tests each lane must turn green in `tests/red/`. The headline number will be nDCG@10 lift of the fine-tuned encoder over zero-shot on held-out customers' later purchases (H&M Personalized Fashion Recommendations, Kaggle). No result exists yet.

The build answers a public job posting at Krea for personalization and recommendation work; Krea's public product has no taste learned from user behaviour (`research/P1.md`).

## Lane P3a: data

`src/tasterank/data/` reads the transactions and articles tables with polars (eager or lazy), assigns customers to train, dev and heldout by the salted hash frozen in `contracts/split.json`, builds each eval split (eligible customers, cold-start count, history, relevant sets, the 84-day candidate pool and the 7-day POP counts), orders histories, builds training pairs and computes the canonical id-list hash. What ran: the 13 P3a red tests and 15 lane tests in `tests/data/`, on CPU against the synthetic fixture `fixtures/shop_like` only. No competition data has been read; the box reads it in P5.

## Lane P3b: train

`src/tasterank/train/` builds customer vectors (recency-weighted mean of L2-normalized image embeddings, `contracts/eval.md`), computes in-batch InfoNCE, wraps the image tower's attention projections (`attn.qkv`, `attn.proj`) with LoRA through peft and freezes everything else, and runs the seeded training loop. Each step encodes every image its batch needs in one forward pass through the LoRA'd encoder, so gradients reach the adapters from both the history side and the target side. Batches hold distinct target articles. The loop refuses pairs dated on or after `train_cutoff` and any checkpoint directory inside the repo (symlinks resolved) before it does any work. It writes `lora.pt` (LoRA tensors only) and `lora.json` (config and per-step losses) to a box-local `out_dir`. `load_lora` rebuilds a trained encoder for evaluation. What ran: the 9 P3b red tests and 31 lane tests in `tests/train/`, on CPU, against the 16x16 `tasterank.tiny` encoder and the synthetic fixture images only. No real encoder has been trained, and no competition data has been read. The box does both in P5.

## Lane P3c: eval

`src/tasterank/eval/` ranks the candidate pool by cosine similarity to a customer vector (ties by article id ascending), ranks POP by last-week count, and computes nDCG@10, recall@12, recall@50 and pool coverage, each a mean over customers. Per-category tables filter both the ranking and the relevant set to one product group. `band` and `lift_band` give the five-seed band and the headline verdict (`lift`, `no lift` or `worse`; a band touching zero is no lift). `make_row` reads `git_sha` and the machine label itself at run time. `write_rows` appends JSON lines and checks every row before it writes any: it refuses id keys at any depth, missing contract fields, unknown row or split names, and NaN. `scripts/eval.sh --fixture <dir>` runs POP and `E0-tiny` on the fixture's dev split through `tasterank.eval.run`. With no arguments it still prints "not an eval phase", because P5 wires the box pipeline. What ran: the 10 P3c red tests and 30 lane tests in `tests/eval/`, on CPU, against the synthetic fixture and the 16x16 `tasterank.tiny` encoder only. One lane test recomputes the fixture's POP row from the CSVs in plain Python, without `tasterank.data`, and gets the same numbers. The fixture numbers are synthetic and measure nothing. No real encoder has been evaluated and no competition data has been read. The box does both in P5.
